# 05 复盘

## 最难的问题

### 怎么证明是模型在做决定

一开始我最担心的是被判成"固定条件分支"。最省事的写法是让检索工具自己判断冲突，直接返回"D01 和 D02 冲突"。这样测试一定能过，但判断其实是代码做的，模型只是把结果复述一遍。

最后定下的原则是：工具只返回事实，不下结论。

- 检索工具返回片段、版本日期和负责部门。
- 读取工具返回原文。
- 是否冲突、要不要换词重搜、失败后要不要重试，都由模型决定。

代码只负责几条硬规则：引用必须和原文逐字一致，引用前必须读过原文，步数用完就停止。

最直接的检验是 C2 和 C3。两个用例问的是同一个问题，代码和提示词都没改，只是 C3 的语料里去掉了 D02。结果模型在 C2 判为冲突，在 C3 直接作答，两条 trace 的动作序列也不同。

另外，同义词表里故意没有放"酒店→住宿"。如果放了，C5 就测不出模型会不会自己改写问题。

### C8 的期望写错了

C8 测的是检索一直失败的情况，最初只接受 `tool_failed` 一种结果。后来重跑时，模型换了一种做法：检索用不了，就用 read_doc 把文档一份份打开，最后在 D05 找到了答案。它同时在 gaps 里说明"没能全量检索，不能排除还有其他版本"。这次被判为 FAIL。

看完 trace 后，我认为模型这样做没有问题：引用是真的，缺口也说明了。"检索坏了就换工具"正是题目想看的"根据工具结果调整动作"。错在期望只认一条预设的路径。

后来把期望改成两种情况：

- 只有检索失败时，放弃或换工具取证都算合格（C8）。
- 检索和读取都失败时，只能承认失败（新增的 C10）。

失败那次的原始记录保存在 `examples/runs/anthropic_failures/`，没有删。

这件事让我意识到，真实模型能走的路比我预设的多。用例应该判断"这个行为是否合格"，而不是"是否走了我预想的那条路"。

### 怎么让人相信运行记录

trace 是 md 和 json 文件，理论上谁都能改。所以我加了一个测试，专门检查已经提交的记录：

- 模型字段是否为 `claude-*`
- 引用能否在原文里逐字找到
- C2 和 C3 的动作序列是否确实不同

记录被手工改过，这个测试就会失败。

## 学到的东西

这次代码大部分是 AI 写的，所以我的收获主要在"怎么判断一个 Agent 做得对不对"上。

**智能放在哪一层，要事先想清楚。** 工具做的判断越多，模型就越像在传话，评审也越看不出它的决策能力。

**结束动作也做成工具。** 我把"结束"做成了 finish 工具，没有让模型自由输出一段话作为最终回答。这样代码能在结束前检查引用，不合格就打回去让模型重做。打回本身又让模型多经历一次"观察结果、调整动作"。

**同一个用例，每次运行结果可能不同。** 开发中重跑过几轮：C1、C3、C7 的步数都变过；C8 有一次答出了答案，另一次选择了放弃。所以跑一次得到 10/10，不能说明结果稳定。

**Mock 只能证明流程能跑通。** Mock 可以离线运行，也方便写测试。但它的规则是照着这 10 个用例写的，不能用它的结果去证明决策质量。

**文档要跟着最后一次运行更新。** 最后做对照检查时，发现文档里写的检索词和最终 trace 对不上。原因是中间重跑过，文档没有跟着改。以后文档里引用运行结果，应该等最后一次运行之后再写。

## 下一步

按重要程度排：

1. 每个用例跑 5 到 10 次，统计通过率和步数分布，找出不稳定的用例。
2. 加更难的冲突用例。现在 30 天对 15 天的冲突太明显。可以试试适用范围部分重叠的情况，比如 D02 只管差旅费，看模型能否按适用范围回答，而不是一律判为冲突。
3. 快到步数上限时提醒模型，让它用已有的证据收尾，而不是被直接截断。C9 现在就是读完两份原文后步数就用完了。
4. 多轮对话时把上一轮的引用也带进去，这样追问时可以少检索一次。
5. 换成真实语料后改用向量检索。同时要重新设计"改写后的相似问题"用例，因为用向量检索时，C5 会变得太容易。
